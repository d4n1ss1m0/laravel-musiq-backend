# Сортировка плейлистов и создание очереди playback

## Вывод и оценка сложности

Добавление сортировки плейлиста с сохранением выбора и созданием очереди в этом порядке — доработка **средней сложности**. Существующая модель playback для неё подходит: состав очереди и позиции уже копируются в отдельную таблицу, а исходный порядок отделён от порядка воспроизведения. Переписывать механизм переходов между треками не требуется.

Основная работа: сохранить настройку конкретного плейлиста, применить единые правила сортировки при чтении списка и создании снапшота, передать параметры через API и проверить взаимодействие с shuffle и ручными изменениями очереди.

Ориентир для backend: **4–7 рабочих дней одного разработчика**, включая миграции, API, регрессионные проверки и Swagger. Это предварительная оценка по коду, а не результат прототипирования. Она предполагает фиксированные пресеты по ручному порядку, названию, первому исполнителю и дате добавления. Frontend, сортировка по полному набору исполнителей и точное воспроизведение состояния экрана при конкурентных изменениях в оценку не входят.

## Требуемое поведение и допущения

**Для обычного плейлиста сохраняем выбранный пресет и используем при следующих открытиях и запусках воспроизведения. Для избранного сортировку определяем по типу плейлиста, без записи настройки.** Это часть предлагаемого решения, а не дополнительная опция.

В этом документе настройка принадлежит паре **пользователь + плейлист**. Например, один пользователь слушает общий плейлист по названию, другой — по дате добавления. Смена сортировки одним пользователем не меняет порядок у остальных. Если нужна единая сортировка для всех посетителей плейлиста, потребуется другой владелец настройки и проверка прав редактирования; этот вариант описан ниже.

Рекомендуемый контракт поведения:

1. При открытии обычного плейлиста сервер возвращает сохранённый пресет пользователя либо `position`. Для избранного всегда возвращается `added`: новые добавления сверху.
2. При выборе другого пресета обычного плейлиста клиент сохраняет его отдельным PATCH, после успеха сбрасывает пагинацию и загруженные страницы и перезапрашивает список с первой страницы. Это действие не вызывает создание снапшота.
3. Снапшот создаётся только при явном действии пользователя: клике по треку **в плейлисте** или кнопке **«Играть плейлист»**. Сервер получает **все** треки плейлиста в выбранной сортировке и создаёт новую очередь.
4. Без shuffle текущий трек остаётся на своём месте в отсортированном списке. Очередь не обрезается до выбранного трека: доступны и предыдущие треки.
5. С shuffle текущий трек перемещается в начало, остальные перемешиваются; выбранная сортировка сохраняется как базовый порядок для выключения shuffle.
6. Смена сохранённой сортировки или состава плейлиста не пересобирает уже работающую очередь. Новая настройка применяется при следующем создании снапшота.

Последний пункт важен: пользовательская настройка плейлиста и уже созданная очередь имеют разный жизненный цикл.

### Избранное (favorite)

Избранное определяется по типу `PlaylistTypes::FAVOURITE`, а не по названию, UUID или наличию записи настройки. Его порядок фиксирован: `track_playlists.created_at DESC` — дата добавления именно в избранное, новые сверху. Это обязательное правило, а не изменяемый пользователем пресет по умолчанию.

Предварительно создавать `user_playlist_settings` для избранного не нужно: запись дублировала бы правило типа и могла бы ему противоречить. Чтение списка, `/playlist/{uuid}/queue` и создание snapshot сначала проверяют тип плейлиста и для избранного выбирают `PlaylistOrderType::ADDED`. Сохранённая настройка и явный override не могут изменить этот порядок.

GET настройки избранного возвращает эффективный `sort: added` и `canChangeSort: false`, не создавая запись. PATCH настройки избранного отклоняется с 422; frontend скрывает выбор сортировки. В snapshot явный `sort: added` допустим, другой пресет отклоняется с 422. Если старая запись настройки избранного существует, при чтении она не учитывается.

При одинаковом времени добавления порядок стабилизируется теми же дополнительными критериями, что и у пресета `added`. Добавление трека в избранное не пересобирает активную очередь. Новый snapshot использует актуальный порядок по дате, а выключение shuffle восстанавливает порядок уже созданного snapshot.

### Когда создаётся новый снапшот

Изменение сортировки, открытие плейлиста и сохранение настройки не должны вызывать `POST /api/playback/snapshot` ни на frontend, ни через побочный эффект backend. Это справедливо и когда активной очереди ещё нет: изменение сортировки само по себе не начинает воспроизведение и не создаёт очередь.

Клик по треку в списке плейлиста явно создаёт новый снапшот с этим треком как текущим, даже если уже играет тот же плейлист или тот же трек. Кнопка «Играть плейлист» тоже явно создаёт новый снапшот по выбранной сортировке. Без shuffle она начинает с первого трека отсортированного списка; клиент передаёт его UUID в обязательном поле `id` текущего API snapshot.

Возобновление воспроизведения через play в плеере и выбор элемента **существующей очереди** работают с текущей сессией через `POST /api/playback/play`, а не создают новый снапшот. Переходы `next/prev` также продолжают использовать прежний порядок очереди.

Пример без shuffle: ручной порядок плейлиста — `[C, A, B]`, сортировка по названию даёт `[A, B, C]`.

| Шаг | Действие пользователя | Список плейлиста | Активная очередь | Новый снапшот |
| --- | --- | --- | --- | --- |
| 1 | Нажал «Играть плейлист» с настройкой «Свой порядок» | `[C, A, B]` | `[C, A, B]`, текущий трек `C` | Да |
| 2 | Выбрал «По названию» | `[A, B, C]` | `[C, A, B]`, текущий трек `C` | Нет |
| 3 | Нажал на трек `B` в списке плейлиста | `[A, B, C]` | `[A, B, C]`, текущий трек `B`, позиция 2 | Да |

Если на третьем шаге нажать «Играть плейлист», также создаётся очередь `[A, B, C]`, но воспроизведение начинается с `A`. Если вместо этого нажать «Далее» в плеере после второго шага, следующим останется `A` из прежней очереди `[C, A, B]`; новый снапшот не создаётся.

## Как playback работает сейчас

| Участок | Реализация | Значение для доработки |
| --- | --- | --- |
| Создание очереди | `POST /api/playback/snapshot`, `SnapshotRequest`, `SnapshotDTO`, `PlaybackController::snapshot()` | Сейчас принимаются `source`, `sourceId`, `id`, `repeatType`, `shuffle`; полей сортировки нет. |
| Выборка источника | `PlaybackService::getTracks()` | Для плейлиста используется `PlaylistRepository::getPlaylistTracks()`, без пагинации. |
| Порядок плейлиста | `PlaylistRepository::getPlaylistTracks()` | Метод возвращает Builder треков с пресетом `PlaylistOrderType`; по умолчанию используется `POSITION`. Настройка пользователя и тип избранного пока автоматически не учитываются. |
| Нумерация | `PlaybackService::getTracks()` | Полученные треки получают последовательные позиции от 1. |
| Хранение | `PlaybackRepository::addSourceTracks()` | `source_position` получает базовую позицию, `playback_position` — позицию в фактической очереди после возможного перемешивания. |
| Текущий трек | `PlaybackService::snapshot()` | Находится по UUID, позиция вычисляется в полученной выборке; при shuffle позиция становится 1. |
| Навигация | `switchTrack()`, `getQueue()`, `PlaybackSession::nextQueueTrackId()` / `previousQueueTrackId()` | Используется сохранённый `playback_position`, повторного чтения порядка плейлиста нет. |
| Выключение shuffle | `PlaybackService::unshuffleTracks()` | Очередь восстанавливается по сохранённому `source_position`, без перечитывания источника. |
| Смена снапшота | `PlaybackService::snapshot()` | Предыдущая сессия удаляется вместе с её очередью, создаётся новая; это также удаляет ручные вставки старой очереди. |

Пример: исходный ручной порядок `[A, B, C]`, выбранная сортировка дала `[C, A, B]`. При запуске `A` без shuffle обе позиции равны `[C:1, A:2, B:3]`, текущая позиция — 2. При запуске с shuffle `source_position` должен остаться таким же, но `playback_position` может стать `[A:1, B:2, C:3]`. После выключения shuffle очередь возвращается к `[C, A, B]`, а текущая позиция `A` становится 2.

Снапшот фиксирует **идентификаторы треков и их порядок**, а не все данные трека. Ресурсы читают актуальные названия, обложки и исполнителей через связь `track`. По миграциям удаление самого трека каскадно удаляет его элемент очереди; полная независимость от удаления треков сейчас не обеспечивается.

## Где сейчас расходятся пути чтения плейлиста

Порядок задан отдельно в трёх местах:

- `PlaylistService::getTracks()` — использует Builder из `getPlaylistTracks()` для поиска по названию и пагинации; пресет приходит из параметра запроса `order`.
- `PlaylistService::getQueue()` — `GET /api/playlist/{uuid}/queue`, полный список идентификаторов и позиций, `orderBy('track_playlists.order')`.
- `PlaylistRepository::getPlaylistTracks()` — общий Builder; playback вызывает его без явного пресета и получает ручной порядок через `get()`.

Если добавить сортировку только в список для интерфейса, playback продолжит играть в ручном порядке. Общий построитель уже есть: `PlaylistRepository::getPlaylistTracks()`. Его следует переиспользовать и в `/queue`, дополнив общей политикой выбора эффективного пресета. Все три пути должны использовать одну политику разрешения настройки и одинаковый SQL-порядок.

Сортировать нужно **до пагинации**, а для снапшота — до назначения `source_position`. Сортировка только полученной страницы на клиенте не гарантирует порядок всего плейлиста. Импорт треков из другого плейлиста имеет отдельную семантику: его существующий ручной порядок не следует автоматически заменять пользовательской сортировкой просмотра.

## Сохранение настройки конкретного плейлиста

Для хранения используем отдельную таблицу `user_playlist_settings`. Настройка не привязана к записи медиатеки: она может существовать у доступного публичного плейлиста, который пользователь не добавлял себе. Удаление плейлиста из медиатеки не сбрасывает выбранную сортировку; удаление самого плейлиста удаляет настройку по внешнему ключу.

| Поле | Назначение |
| --- | --- |
| `id` | Первичный ключ. |
| `user_id` | Пользователь, выбравший сортировку. |
| `playlist_id` | Плейлист, к которому относится выбор. |
| `sort` | Значение пресета `PlaylistOrderType`: `artist`, `title` или `added`. Значение `position` используется в API для сброса и не сохраняется в таблице. |
| `created_at`, `updated_at` | Время создания и изменения настройки. |

Нужны уникальность `(user_id, playlist_id)` и внешние ключи с удалением настройки при удалении пользователя или плейлиста. **Таблица хранит только отклонения от стандартной сортировки. Для обычного плейлиста отсутствие записи означает «Свой порядок»: `position`, то есть `track_playlists.order ASC`.** Массовый backfill всех сочетаний пользователей и плейлистов не нужен.

Жизненный цикл записи:

- Открытие плейлиста и чтение эффективной настройки ничего не создают. Для отсутствующей записи сервер возвращает `position`; `firstOrCreate` при чтении не используется.
- Выбор нестандартной сортировки выполняет upsert по `(user_id, playlist_id)`.
- Возврат к «Свой порядок» удаляет запись этой пары. Если записи уже нет, операция всё равно успешна.
- Создание snapshot читает эффективную сортировку, но не создаёт запись настройки.
- Сброс настройки не меняет уже созданную очередь; следующий snapshot без явного override использует ручной порядок плейлиста.

В настройке хранится только пресет `sort`, а не список UUID и не переписанный `track_playlists.order`. Поле `order` остаётся общей ручной последовательностью плейлиста. Сортировка просмотра не должна запускать существующий `PUT /playlist/{uuid}/order`.

Для сохранения достаточно права **просматривать** плейлист: слушатель публичного плейлиста должен иметь возможность сохранить собственную сортировку. Привязывать этот маршрут к `CanManagePlaylistMiddleware` не следует. `user_id` берётся из авторизации, клиент не выбирает владельца настройки. При потере доступа к приватному плейлисту чтение его треков и создание снапшота всё равно должны запрещаться, даже если настройка сохранилась.

Рекомендуемые новые маршруты:

```http
GET /api/playlist/{uuid}/sort
PATCH /api/playlist/{uuid}/sort
```

Ответ GET содержит эффективный `sort` и `canChangeSort`: для обычного плейлиста `true`, для избранного `false`. При отсутствии записи применяется правило типа плейлиста. PATCH принимает, например:

```json
{
  "sort": "title"
}
```

PATCH выполняет upsert для нестандартной сортировки. Для сброса клиент отправляет:

```json
{
  "sort": "position"
}
```

Сервер удаляет настройку текущего пользователя для этого плейлиста и возвращает эффективное значение `position`. Направление фиксировано пресетом; отдельные `sortDirection` и `sort_direction` не принимаются. В обоих случаях PATCH возвращает эффективную настройку независимо от наличия записи в таблице.

Альтернатива отдельному GET — включить настройку в ответ существующего `GET /playlist/{uuid}`; это сократит число запросов при открытии экрана. Конкретный вариант нужно согласовать с frontend.

**Если сортировка должна быть общей для плейлиста**, поля можно хранить непосредственно в `playlists`, а менять их сможет только владелец или другой пользователь с правом управления. В таком случае смена настройки влияет на новые открытия и снапшоты всех слушателей. Структуру очереди менять всё равно не потребуется. Основная рекомендация этого документа — персональная настройка пары пользователь/плейлист.

## Единые правила сортировки

Пресет определяет и поле, и единственное разрешённое направление. По двум полям enum искать не требуется: модель приводит `sort` к `PlaylistOrderType`, а SQL и направление задаются правилами пресета.

| Пресет | Поле для сортировки | Направление |
| --- | --- | --- |
| `position` | `track_playlists.order` | ASC — «Свой порядок». |
| `artist` | Имя первого исполнителя | ASC — первый исполнитель определяется минимальным `track_artists.id`, как в связи `Track::artists()`. |
| `title` | `tracks.name` | ASC. |
| `added` | `track_playlists.created_at` | DESC — новые добавления сверху. |

`artist` использует коррелированный подзапрос с `LIMIT 1`, чтобы не размножать строки треков при нескольких исполнителях. Треки без исполнителей остаются в выборке. Правила регистра, языка и расположения NULL должны быть одинаковыми для всех путей чтения.

После основного критерия Builder добавляет уникальный `track_playlists.id`: DESC для `added`, ASC для остальных пресетов. При одинаковой дате добавления запись с большим ID идёт выше, в том числе в избранном. Этот критерий обеспечивает стабильный порядок при равных названиях и датах, включая массовое добавление с одинаковым timestamp. Ручная позиция не влияет на порядок совпадений других пресетов.

Направление отдельно в БД не сохраняем: при фиксированных пресетах оно дублирует правила enum. Если появится независимый выбор ASC/DESC, это потребует отдельного расширения контракта. Созданные ранее миграция и модель пока содержат `sort_direction`; перед внедрением их нужно привести к этому решению. Сам enum пока не содержит метода `direction()`; направление сейчас задано в репозитории.

Поля SQL выбираются только из разрешённого набора пресетов. При смене пресета нужно заменить основной ORDER BY, а не дописывать его после ручного порядка.

## Изменения в playback

Предлагается дополнить `SnapshotRequest` и `SnapshotDTO` необязательным `sort`, затем передавать их через `PlaybackController::snapshot()` в сервис. Для `source=playlist` эффективная сортировка определяется так:

1. Тип избранного — всегда `added`; несовместимый явный пресет отклоняется.
2. Для обычного плейлиста — явно переданный пресет экрана, если он указан.
3. Сохранённый пресет пользователя для этого плейлиста.
4. Стандартное значение `position`.

Явный пресет позволяет создать очередь в порядке, который пользователь видел при нажатии, даже если на другом устройстве уже изменили сохранённую настройку. Он сам по себе не сохраняет пользовательскую настройку: сохранение выполняется отдельным PATCH. Направление всегда определяется пресетом; отдельного override направления нет.

Пример **предлагаемого**, пока не реализованного запроса:

```json
{
  "source": "playlist",
  "sourceId": "019fc713-f522-73fc-8f2d-b2938bdaa5a0",
  "id": "6654fcfe-cb4f-4c8f-951c-57eb5bde50a1",
  "repeatType": "off",
  "shuffle": false,
  "sort": "title"
}
```

Для источников `artist` и `track` следует сохранить текущий порядок, а явно переданные плейлистные параметры отклонять валидацией. В существующем API нет поддержки сортировки; старые клиенты после внедрения будут использовать сохранённую настройку, а при её отсутствии — прежний ручной порядок.

Алгоритм сервиса: проверить доступ к источнику, получить отсортированный полный набор, убедиться, что выбранный UUID в нём есть, назначить базовые позиции и только затем применить shuffle. Сохранение очереди через `addSourceTracks()` уже подходит: изменения его структуры для сортировки не обязательны.

Поля сортировки в `playback_session_tracks` добавлять не требуется. Позиции уже достаточны для воспроизведения и восстановления порядка. При необходимости показывать настройку активной сессии на другом устройстве можно дополнительно сохранить `source_sort` в `playback_sessions` и отдать их через `PlaybackSessionResource`. Это будет описание параметров создания снапшота; после ручного перемещения оно не гарантирует, что текущая очередь всё ещё отсортирована по этому ключу.

## Shuffle, ручная очередь и изменение плейлиста

| Действие | Ожидаемое поведение |
| --- | --- |
| Создать снапшот без shuffle | Обе позиции отражают выбранную сортировку. |
| Создать снапшот с shuffle | `source_position` отражает сортировку, текущий трек первый в `playback_position`. |
| Включить и выключить shuffle | Восстановить порядок снапшота, не применять заново актуальную настройку плейлиста. |
| Изменить сохранённую сортировку | Текущая очередь не меняется; новые списки и снапшоты используют новую настройку. |
| Добавить или убрать трек из плейлиста | Существующая очередь не пересобирается автоматически. Удаление самого объекта Track — отдельный случай из-за каскадных связей. |
| Создать новый снапшот | Текущая сессия полностью заменяется, включая ручные вставки, как и сейчас. |
| Переместить элемент очереди без shuffle | Сохранить действующее поведение: новый порядок становится базовым для этой сессии. Настройка плейлиста не меняется. |
| Переместить элемент при shuffle | Меняется порядок воспроизведения; выключение shuffle восстанавливает базовые позиции. |

`source_position` нельзя описывать как неизменяемый оригинал: `moveTrack()` без shuffle переписывает его из `playback_position`, а ручные вставки сдвигают исходные позиции. Если потребуется отдельная команда «вернуть первоначальную сортировку» после ручных правок, понадобится дополнительное хранение исходного порядка или иной явный контракт.

## Найденные риски текущего кода

Это результаты статического чтения, без воспроизведения на рабочей базе:

- **Нет тестов playback в текущем дереве tests.** Регрессия затрагивает сразу позиции, перемешивание и ручные вставки; одного теста сортировки недостаточно.
- **У snapshot нет аналогичной проверки доступа к приватному плейлисту.** Маршруты чтения плейлиста используют `CanViewPlaylistMiddleware`, но `SnapshotRequest` проверяет только существование источника и принадлежность трека. При доработке нужно переиспользовать проверку доступа, например существующее правило `CanViewPlaylist`.
- **Возможна гонка между валидацией и чтением источника.** `snapshot()` получает треки до транзакции изменения сессии. Если выбранный трек удалили между запросами, обращение к `$currentTrack['id']` может произойти на `null`. Нужен контролируемый ответ с сохранением прежней сессии.
- **Блокировка пользователя защищает сессию, но не изменения плейлиста.** Даже одинаковые правила сортировки не гарантируют идентичность ранее показанного экрана и более позднего снапшота при конкурентных добавлениях или переименованиях. Для строгой гарантии потребуются версия источника и согласованная проверка версии; это отдельный объём работ, не обязательный для обычной сортировки.
- **`addToQueue(next)` предполагает наличие следующего элемента.** При текущем треке в конце очереди `$nextTrack` может оказаться `null`. Этот существующий крайний случай нужно покрыть при регрессии.
- **Перестановки используют ограничения уникальности и PostgreSQL SQL.** В `updatePlaybackPositions()` есть `::bigint`, а позиции обновляются через временное смещение. Проверки shuffle/move следует выполнять на PostgreSQL, а не ограничиваться SQLite.
- **Большие плейлисты загружаются целиком и вставляются одним bulk insert.** Новая SQL-сортировка добавит стоимость, но сама модель полной загрузки уже существует. Индексы и размер пакетов вставки стоит выбирать после измерений на реальных объёмах.

## Поиск и точное соответствие экрану

Сейчас список треков плейлиста поддерживает `query`, а snapshot этот фильтр не принимает. Предлагаемый первый этап сохраняет это поведение: сортировка относится ко всему плейлисту, а очередь включает весь источник, даже если на экране была открыта страница поиска.

Если требуется проигрывать только найденные треки, фильтр тоже должен стать частью контракта snapshot, общей выборки и проверки выбранного трека. Это отдельное продуктовое решение. Нельзя отправлять в snapshot только UUID загруженной страницы: очередь потеряет остальные страницы.

Даже без фильтра frontend должен передавать выбранный UUID, а не номер строки в списке: `currentPosition` вычисляется backend в полном отсортированном наборе.

## План реализации и проверки

| Этап | Изменения |
| --- | --- |
| 1. Контракт | Зафиксировать пресеты с фиксированными направлениями, правило избранного, порядок равных значений, поведение поиска и персональную принадлежность настройки. |
| 2. Настройки | Миграция `user_playlist_settings`, модель/репозиторий, GET без создания записи, PATCH с upsert нестандартной сортировки и удалением при `position`, права доступа. |
| 3. Общая выборка | Один механизм сортировки для списка, `/playlist/{uuid}/queue` и источника playback; сортировка до пагинации. |
| 4. Снапшот | Request, DTO, controller, разрешение типа избранного/override/сохранённого значения, защита от отсутствующего трека и приватного источника. |
| 5. Регрессия | PostgreSQL-тесты списка, сохранения настройки, snapshot, shuffle, навигации, ручных изменений. |
| 6. Интеграция | Swagger для настроек и snapshot; frontend сохраняет выбор и восстанавливает его при открытии. Snapshot вызывается только по клику на трек в плейлисте или «Играть плейлист», с параметрами видимого порядка; смена сортировки его не вызывает. |

Минимальные критерии приёмки:

1. Сортировка сохраняется для пользователя и конкретного плейлиста, переживает повторное открытие; не затрагивает другого пользователя или другой плейлист.
2. Отсутствие настройки даёт `position`; открытие плейлиста и создание snapshot не создают запись. Повторное сохранение нестандартной сортировки обновляет одну запись без дублей. Выбор «Свой порядок» удаляет запись только текущей пары пользователь/плейлист; повторный сброс успешен. Текущая очередь не меняется, следующий snapshot использует ручной порядок. Направление отдельно не принимается.
3. Нельзя сохранять настройку или создавать snapshot недоступного приватного плейлиста.
4. Для каждого пресета список, полный список идентификаторов и snapshot совпадают по порядку; равные значения имеют стабильную последовательность.
5. Запуск трека со второй страницы создаёт полную очередь и корректную текущую позицию.
6. Shuffle on/off возвращает базовый порядок выбранной сортировки и сохраняет текущий трек.
7. Изменение сортировки не вызывает snapshot, не меняет активную очередь, текущий трек или позицию воспроизведения и не создаёт сессию при её отсутствии. После «Свой порядок → snapshot → По названию» очередь остаётся в ручном порядке. Клик по треку в плейлисте или «Играть плейлист» создаёт новый snapshot по названию. Обычный play в плеере, выбор элемента существующей очереди и `next/prev` новый snapshot не создают.
8. `next`, `prev`, repeat queue/track, ручные next/tail и move сохраняют согласованность `current_track_id` и `current_position`.
9. Отдельно покрыты пустой источник, один трек, отсутствие выбранного трека и вставка next в конце очереди.
10. Неизвестные пресеты и отдельные параметры направления отклоняются; сортировка не переписывает ручной порядок плейлиста.

11. Избранное без записи настройки возвращает `added` и `canChangeSort: false`. Список, `/queue` и новый snapshot используют дату добавления DESC; одинаковые даты дают стабильный порядок. PATCH и несовместимый snapshot override отклоняются, настройки не создаются. Правило действует и при наличии старой записи настройки. Shuffle on/off восстанавливает порядок snapshot, добавление в избранное не меняет активную очередь.
